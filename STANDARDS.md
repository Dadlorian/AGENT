Generated by `tools/standards.py render` at 558ba51 from `docs/standards/standards.json`, the skill contracts, `kb/research.jsonl` and `examples/*/README.md`. Do not edit by hand; edit the data file.

One list of every standard known to this platform, whether or not the platform uses it, so the gap between known and aligned is visible. Origin owner 2026-09-08: keep a standards file that tracks which standards align with our tool and which do not, and keep improving it. Taken further here (proposed): each row is computed against the knowledge base, the skill contracts and the examples, so the alignment column is measured rather than asserted.

## How to read a row

| Column | Means |
|---|---|
| Status `contract` | a skill contract names the standard (E-standard entity, version, sources), so the platform claims it |
| Status `researched` | research records exist in kb/research.jsonl and no skill contract names it |
| Status `known` | listed here only, no research record yet: a gap to research, never to invent |
| Position `adopt` | the platform should name it in a contract |
| Position `hold` | named where it is, no wider use planned |
| Position `watch` | too early or too contested to name, re-check at a phase boundary |
| Position `decline` | considered and not adopted, with the reason |
| Version | what the citing contracts claim; every version is unverified until the specification is fetched (STATUS row 14) |
| Records | research records that match; the first ids are listed so a reader can `python3 tools/kb.py show <id>` |
| Examples | example folders whose README names the standard |
| Journey | the steps in JOURNEY.md that expose it |

## Areas with no open standard

The contract is the platform's own here, marked proposed, and re-checked at each phase boundary.

| Area | Owning skill | Note |
|---|---|---|
| evaluation | `cap-evaluation` | case sets, baselines and verdicts have tools (Inspect and similar) but no specification; the contract is the platform's own and is marked proposed |
| durable execution | `cap-durable-execution` | checkpoints, resume points and compensation are a pattern; no body publishes a wire or document format |
| memory | `cap-state-persistence` | memory items are vendor-specific everywhere; the platform stores opaque records at a pinned snapshot and defers nothing |
