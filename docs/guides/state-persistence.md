## What a caller uses

| Operation | Input | Output | Origin |
|---|---|---|---|
| append (proposed operation set; no standard fixes a call surface for this capability, so the set below is ours) | an opaque record body, its kind tag, the partition it belongs to, the record id the writer expects to be the current head, and the fencing token the writer holds | the accepted record's content-addressed id and the new head, or a rejection naming which of the two conditions failed: the head moved, or the token is behind one already seen | proposed |
| resolve_head (proposed) | a partition | the current head as tree size, root hash, chain digest and whether it is sealed; this is the only call in the set that is allowed to be non-deterministic, and it is made once before a plan is computed | proposed |
| read_at (proposed) | a selector and a head | the records the selector matches, deterministic at that head: the same head returns the same answer forever, whatever has been appended since | proposed |
| prove (proposed) | a record id and a head | an inclusion proof that the record is in the log at that head, checkable by a party that holds the record, the proof and the head and nothing else; never a re-read of the log | proposed |
| prove_consistency (proposed) | an earlier head and a later head | a proof that the later log extends the earlier one with nothing removed and nothing reordered, which is how a reader who saw the log yesterday checks it today without storing it | proposed |
| redact (proposed) | a record id and the authority under which the body is being removed | a tombstone that keeps the record id and the chain position and drops the body, so every prior proof still verifies; the store has no delete | proposed |

From `cap-state-persistence` contract.operations; a row marked proposed is this repo's design, not a sourced fact.

## Adapters

| Role | Entity | Exposes | Cannot |
|---|---|---|---|
| today | E-adapter-jsonl-hash-chain | The recorded adapter is JSONL + hash chain: one append-only local file per store, order carried by position in the file, identity carried by sequence number, integrity carried by a digest of the previous record folded into the next one | Cannot serve prove or prove_consistency at all: the only integrity operation the shape admits is a sequential rehash of every record, performed by our own reader over a file only we hold |
| second | E-swap-candidate-object-store | A content-addressed log over an object store: each record is an immutable object named by the digest of its canonical bytes, order is carried by an append-only Merkle tree rather than by file position, and the head is a small signed object | Cannot rely on write order, on reading the previous line to find the head, or on a single process owning a file: objects arrive out of order, a listing is eventually consistent, and the head has to be a compare-and-swap on one small object rather than a position |

From `cap-state-persistence-implement` adapters. Product names live only here and in the harness adapter files.
