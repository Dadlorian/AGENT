# How sourcing works here, and how not to break it

The one rule: **a claim is either cited to a record with a verbatim quote, or explicitly marked
`proposed`.** Everything below exists to make that rule mechanically enforced rather than a habit.

Written 2026-09-09 from a survey of the tools themselves, not from memory. Every command listed
was run. Re-verify before trusting any count on this page.

## The instruments, in the order work moves through them

### 1. Research records — where an outside claim enters

| | |
|---|---|
| Written to | `kb/research/<lens>.jsonl`, one file per lens (64 files) |
| Schema | `schemas/research.schema.json` — `id`, `type`, `lens`, `topic`, `query`, `url`, `title`, `snippet`, `status`, `agent`, `date` |
| Merged by | `python3 tools/kb.py merge-research` → `kb/research.jsonl`, sorted by id, deduplicated, chained |
| Ids | `X-<lens>-<nnn>` |

`status` is a closed enum: `search-only`, `fetched`, `blocked`. A record that claims `fetched` or
`blocked` must also carry an `egress_ref` naming a `G-#####` decision in `kb/egress-log.jsonl`,
reconciled by `tools/reconcile_egress.py`.

**Current state: 817 `search-only`, 1 `blocked`, 0 `fetched`.** The snippet in every record is
search-result text, not text read from the page. The chain is honest about this — it does not
claim the page was read — but "sourced" here means "a search returned this", which is weaker
than the methodology is built to support. The `fetched` path is fully implemented and unused.

### 2. The knowledge base — the chain

Records are hash-chained: each carries `prev` (the previous record's hash) and `hash` (SHA-256 of
its own canonical JSON, all fields except `hash`, sorted keys). The first record's `prev` is the
literal `"genesis"`. Chain heads are stored in `kb/meta.json`.

**Derived — regenerated by `kb.py build`, so a hand-edit is destroyed:**
`kb/facts.jsonl` (from `PASS.md`), `kb/entities.jsonl`, `kb/edges.jsonl`,
`kb/target-facts.jsonl` (from `TARGET.md`), `kb/reference-facts.jsonl`, `kb/meta.json`.

**Additive — never touched by `build`:**
`kb/ledger.jsonl` (append-only), `kb/research.jsonl` (written by `merge-research`),
`kb/architecture.jsonl` (written by `import-blueprint`).

Anything new belongs in the additive class, with its own importer.

```
python3 tools/kb.py verify          # chains intact, source hash matches, every fact matches
                                    # its lines, rebuild is identical
python3 tools/kb.py ledger-verify   # ledger chain intact
```

`verify` re-derives the whole KB in memory and compares hashes. That is the check that catches a
hand-edit to a derived file.

### 3. Citation validation — the anti-fabrication gate

```
python3 tools/validate_skills.py
```

Two rules do the work:

1. every id in a `sources` array must resolve to a real KB record;
2. **every `quote` must be a verbatim substring of a cited record's text.**

The second is the load-bearing one. A paraphrase fails. A quote that drifts from its snippet
fails. This is why a claim cannot be invented and dressed as sourced.

### 4. Ceremonies — review and improve, with a test on the reviewer

A section closes with two records under `kb/ceremonies/`:

- `ceremony-<N>-review.json` — `findings[]`, each with `id`, `skill`, `location`, `severity`
  (block/fix/nit), `finding`, `evidence`, `suggested_change`
- `ceremony-<N>-improve.json` — `applied[]` (`finding`, `change`, `files`) and `declined[]`
  (`finding`, `why`)

```
python3 tools/check_ceremony.py <review.json> <improve.json>
```

Enforces: the review is non-empty, every finding id appears exactly once across applied and
declined, no unknown ids, and every file named in an applied entry exists.

**The reviewer is itself tested.** `tools/plant.py plant <skill>` inserts two known defects — one
misquoted source, one claim whose source reference was removed. `plant.py check <review.json>`
exits 1 if the review missed them, and the review is discarded and re-run. State lives in
`state/plants.json`; `plant.py unplant` restores.

Measured effect, from `python3 tools/ceremony_check.py`:

| Ceremony | 1 | 2 | 3 | 4–6 | 7 | 8 | 9 | 10 |
|---|---|---|---|---|---|---|---|---|
| Findings per skill | 1.00 | 1.00 | 0.38 | 0.07 | 0.14 | 0.00 | 0.12 | 0.00 |

### 5. Evidence — what makes a green result mean something

From `.claude/skills/build-evidence`: every piece needs a criterion a machine can check, a
**deliberate breakage that makes that criterion fail**, and the recorded output of *both* runs.
A gate that passes but has no recorded failure run is not evidence.

`status` separates `claimed` from `measured`. A `measured` record carries the time, the session,
and whether the tree was dirty.

### 6. Litmus — scoring the distance to the future state

`docs/litmus/frame.json` fixes a closed scale:

| Score | Label | Means |
|---|---|---|
| -1 | misaligned | Built toward something that would not work. An error to correct, not a gap to fill. |
| 0 | absent | Nothing exists for this question. |
| 1 | exists | Something exists, but its use is nominal or its direction cannot be judged. |
| 2 | aligned | Exists and is directionally aligned with the future state stated. |
| 3 | leading | At or beyond the future state stated, with the evidence to show it. |

Sections carry 4–8 questions across at least 4 of six angles (`presence`, `depth`, `boundary`,
`guarantees`, `usage`, `direction`), and must include `depth` and `usage`.

An answer carries `score`, `label`, `evidence[]`, `finding`, and — when score ≤ 1 — a `gap`.
An evidence row is either `path` + `quote` (verbatim substring of that file) or
`command` + `last_line` (**the command is re-run and the last line must still match**).

```
python3 tools/litmus_check.py check                 # 23 sections, 144 questions, 0 errors
LITMUS_ANSWERS_DIR=answers-v2 python3 tools/litmus_answers.py check
python3 tools/spot_check.py sample litmus 15        # ids only, seeded from git HEAD
python3 tools/spot_check.py compare litmus <verifier.jsonl>
```

`litmus_check.py` additionally enforces coverage against PASS.md rows, that every cited id
resolves, **contamination** (no section text may name a skill, harness, tool or repo doc), and
distinctness (no two questions repeat across sections).

The spot check is the honesty gate: an independent verifier is given only question ids, never the
existing answers, and re-answers them. More than 20% contradictions fails the sample.

Evidence is re-verified at check time, not trusted from when it was written: every `command` is
re-executed (180s timeout) and every `quote` is re-searched in its file. That is why answers rot.
`answers-v2` currently fails — roughly 36 of 144, split across output drift, paths that no longer
exist, and quotes that no longer match. Two runs of the same check minutes apart gave 39 then 36,
which is the fragility itself: evidence commands that count things in the tree move while other
work runs. `NEXTSTEP.md` item B.1 proposes the durable fix — stamp `measured_at` on each evidence
row and re-run at that commit in a worktree before calling a mismatch an error.

### 7. Closing — the only way work lands

```
do the work → review → improve → ledger record → checkpoint
```

`python3 tools/kb.py ledger '<json>'` appends one `L-#####` record carrying the time, git commit,
tree hash, dirty flag, and `kb_heads` — a snapshot of every chain head at that moment. That is
what ties a claim to the exact state of the KB when it was made.

`bash tools/checkpoint.sh "<message>" <paths>` takes a lock, runs `validate_skills.py` and
`kb.py verify`, **refuses on red**, then stages your paths *plus* `kb/ledger.jsonl` — so the
ledger cannot drift from the tree — commits and pushes.

## How this breaks

- Citing an id that was never merged → `validate_skills.py`: "cites unknown id"
- Editing a quote so it no longer matches its snippet → "quote is not a verbatim substring"
- Hand-editing a derived KB file → `kb.py verify` fails on rebuild-is-identical
- Duplicate `X-` ids across research files → `merge-research` exits 1
- A `fetched` or `blocked` record with no `egress_ref` → `reconcile_egress.py` fails
- A finding neither applied nor declined → `check_ceremony.py` fails
- A review that misses both plants → discarded, re-run
- An evidence command whose output moved → `litmus_answers.py` errors, scorecard refuses to write
- Skipping `checkpoint.sh` → ledger diverges from the tree

## Extending this to the reference architecture

The reference model (`docs/reference/reference-model.json`, 40 cards) is currently **40
uncited claims**. To bring it in without weakening anything above:

1. **Import as additive, never derived.** Copy the `import-blueprint` pattern: a new importer
   writes `kb/reference-model.jsonl` with its own id prefix, chained, each record carrying
   `sources`. It must not write to `entities.jsonl` or `edges.jsonl`, which `build` overwrites.
2. **Cite or mark proposed, per card.** `tools/resolve_reference_model.py` proposes evidence with
   scores; a score is a shortlist, never a citation. Each card needs a decision recording the
   `F-`/`T-`/`X-`/`E-` ids that justify it, or `origin: proposed`.
3. **Answer the gaps as research records first.** A card with no evidence needs an `X-` record in
   `kb/research/<lens>.jsonl` before it can be cited — same schema, same merge, same chain.
4. **Score against the future state.** New litmus sections extend `CANON` in
   `tools/litmus_check.py`, add a section to `docs/litmus/parts/<part>.json`, then answer every
   question with evidence rows. `frame.json` does not change.
5. **Close it the same way.** Review, improve, ledger, checkpoint.

The reference model is the future state. The litmus score is the distance to it. Neither is
evidence on its own.
