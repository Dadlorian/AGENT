# steer — approve, edit, reject, retry, escalate; and the operator's reconnect, restart and replace of a stuck unit

Two people steer this run. A reviewer stands in front of one side-effecting step
and approves it, edits it or rejects it; an operator finds the cell that stopped
answering and reconnects to it, restarts it or replaces it. Both are actions,
so both are decided before they happen, by one decision point that no door and
no adapter goes around and that no member of the caller's document can disable.
`bash examples/steer/test.sh` is the visible check.

Every row below is cited to a knowledge-base id, a research id, or a file with a
verbatim quote, or it says **proposed** and gives its reasoning. File evidence is
cited as `REF-<path>#<anchor>`, so one grep over this directory finds every id a
row carries and `provenance.json`'s `cites` list can be checked against it in
both directions (`test.sh` section 11). Nothing here names a product or a policy
language outside the adapters and standards tables.

## 3. The call

Four entries cover nearly every situation and all four enter through the same
shape (`T-t6-02` "Four entries cover nearly every situation: a human, an event, a
schedule (time), and an external system or agent."). Each document validates
against `REF-examples/end-to-end/schemas/entry.schema.json` with that example's
own validator; the steer declaration inside `payload.steer` validates against
`schemas/steer.schema.json` with the *same* validator. No client library from
this repository is involved (`F-b1-05` "A caller needs no client library we
wrote.").

| Door | The one line a caller writes | The document behind it | What is different | What is identical |
|---|---|---|---|---|
| human (a shell or an IDE) | `python3 examples/steer/run.py --entry examples/steer/entries/human.json` | `entries/human.json` — `user:corey`, one direct hop, no mandate | approves at the gate, from a `stream` surface, and steers no cell | one unit declaration, one envelope shape, one decision point, one rule set |
| event | `python3 examples/steer/run.py --entry examples/steer/entries/event.json` | `entries/event.json` — `service:checkout-alerting`, two hops | the reviewer **edits**: the run continues with the reviewer's component, not the proposed one; the first turn stalls and the operator **reconnects** | the same unit declaration, envelope shape, decision point and rule set |
| schedule | `python3 examples/steer/run.py --entry examples/steer/entries/schedule.json` | `entries/schedule.json` — `schedule:nightly-change-guard`, acting on a user's behalf | nobody is at a screen: the ask reaches its deadline and the unit ends `failed`; the stalled cell is **restarted** from its checkpoint | the same unit declaration, envelope shape, decision point and rule set |
| external (another agent) | `python3 examples/steer/run.py --entry examples/steer/entries/external.json` | `entries/external.json` — `agent:partner-sre-bot`, three hops, and two members nothing reads: `parent_correlation_id` and `depth: 1`, both written up below | **rejects**, is **retried** once, then **escalates** one step to the authority the unit names; the stalled cell is **replaced** | the same unit declaration, envelope shape, decision point and rule set |
| the unit behind all four | `intent.workflow_ref` → `units/steer-checkout-coupon-fix.json` | the task specification: the isolation declaration, three ceilings, the steering policy, the gate, the effect it stands in front of, and the interventions the unit permits | nothing | one declaration, four doors |

Measured, not asserted: the four doors carry four actors, four run ids and four
correlation ids through one unit, and the effect decision is identical in
point, action, effect, rule and resource at every one of them (`test.sh` section
1). Not byte-identical: the four inputs carry four run ids, four correlation ids
and four entry kinds, so they hash to four digests — which is the point of the
next sentence. The door is an attribute of the input and no rule of either
bundle reads it, which is the same section's second check.

### What `payload.steer` declares, and where each field is read

| Field | Read at | What changes when it changes | Proved by |
|---|---|---|---|
| `surface` | `main()`, choosing the human-interaction adapter | `stream` declares a 65536-byte edit limit and applies a 400-byte body; `parked-item` declares 256 and refuses the same body at 422 rather than truncating it — one store, two projections of it | `test.sh` section 4, differential |
| `decision` | `ask_and_decide()`, at the decision the surface carries | approve continues with the proposed artifact, edit with the reviewer's own, reject spends an attempt and turns the disposition to retry, none lets the ask reach its deadline | `test.sh` sections 4 and 5, one run per value |
| `decision_body` | `store.apply()`, checked against the ask's response schema | the body becomes the artifact on edit; a body the schema rejects is refused before the run continues | `test.sh` section 4 |
| `decision_delay_seconds` | `ask_and_decide()`, against `gate.deadline_seconds` | past the deadline the ask is terminal, a late decision is 504, and the unit ends failed rather than waiting; short of it the ask is still open, the sweep is refused 422 by the store that owns the deadline, and no `ask.expired` event is emitted | `test.sh` section 5, differential, both sides |
| `intervention` | `one_attempt()`, when the turn did not finish | reconnect keeps the unit id; restart returns a new unit at the checkpoint digest; replace returns a new unit at the stuck unit's own digest; none does nothing | `test.sh` section 6, one run per value |
| `stall_first_turn` | `one_attempt()`, choosing the turn's operation length | true runs the first turn past the unit's wall ceiling and the boundary ends it `terminated` by the budget ceiling; false ends `end_turn` with fewer frames | `test.sh` section 6, differential |
| `policy_version` — **absent by design** | the schema, at admission | a caller that adds it is refused 422: a caller cannot pin, choose or soften the rules its own action is judged by | `test.sh` section 8 |

| Isolation and agent runtime | `harness/containment/adapters/dryrun.py` — a machine granted, a process held open, checkpoint, restore and clone served | `CELL=dryrun\|second` | `adapters/second.py` — capability grants instead of a machine, single-shot, nothing running to checkpoint: pause, resume and fork return a typed unsupported result. **Proved here**: `test.sh` section 6 runs the schedule door on both and compares the lifecycle offered, the checkpoint and the operator's verb |
| Model access | `harness/gateway/adapters/dryrun.py` — a completion returned in process, priced from the routing table | its own adapter name | `adapters/second.py` — a provider's asynchronous batch route where cost is committed at submit and reconciled at claim. Proved in that harness's own gate, not here |
| Errors | `harness/errors` — one construction point and a closed registry | — | — (one construction point; it has no second implementation to swap) |

No live credential, live endpoint or vendor client is reachable from this
directory: the dry-run adapters run in process with no network, and the call
shape is the one the live adapter takes (`F-b1-04` "Swappability is a tested
property, not an intention.").

### Run steps

`test.sh` clears `out/` before it starts, and gives every run its own `--ledger`
name. The steps below do the same, and for the same reason: the parked-ask store
is durable and its path is derived from the ledger name, so two runs that share
one ledger name park one ask, and the second is a replay refused at 409. Run in
the order they are numbered, from the repository root, each one lands in its own
receipt prefixed with `run-` to avoid conflicts with the visible check, and step 12 reads the one step 2 wrote.

### Carried and not consumed

| Field | Where | Why it is here anyway | Research query |
|---|---|---|---|
| `context.entry_kind` | the decision input | It is on the input on purpose and read by no rule, which is the property this area wants: one input shape for all four doors, "with the entry itself as an attribute rather than a different shape". `test.sh` section 1 asserts both halves — that no rule of either bundle names it, and that the four doors get the identical decision — so its absence from the rules is measured rather than assumed | should a member no rule may read be carried on the decision input at all, or does an attribute that exists only to be ignored belong in the record instead |
| `context.delegation_depth` | the decision input | The chain's length is on the input and the mandates derived from it are what the rules read; no rule bounds the depth, although the maximum-depth question is an open one on file. Nothing here would behave differently if the field were deleted | what bound does a platform put on delegation-chain depth, where is it enforced, and does a decision point or a token exchange own the check |
| `correlation.depth` | the entry envelope | The caller declares a hop count and the platform derives its own: every rule, record and decision reads `len(actor.delegation_chain)`, so the declared member reaches nothing. Measured rather than asserted - the external door run with `depth: 99` and with the member deleted returns the same status, the same nine decisions and the same stream, and every record of both carries the derived depth 3 (`test.sh` section 1b) | should a caller-declared depth bound anything at all, or is a hop count the platform derives from the chain the only one that may decide - and if the two disagree, which is the audit's |
| `envelope_version` | the entry envelope | The shared entry schema fixes it as a `const`, like `budget.on_exceed` below: one legal value, so reading it could only confirm the constant. It is here because the day there are two versions it is the member that says which shape arrived | how does an envelope version stop being a constant - what admits a second version, who maps the older shape forward, and is that a validator's job or an intake adapter's |
| `gate.proposed.irreversibility` | the unit's gate | The capability refuses a value outside reversible, compensatable and irreversible, and the ledger records it, but nothing here branches on it: this gate parks a person unconditionally. A reversible action would reach the same pause | should the irreversibility class decide whether an action is gated at all, or only what the compensation is - and what fires the gate for an action nobody classified |
| `steering.escalation.trigger` | the unit's steering policy | It travels from the declaration onto the escalation record, which `test.sh` asserts, and it is a sentence rather than a condition: what actually fires the escalation is the permitted attempts being spent. | `budget.currency` | the entry envelope | Every price in this example is in micros and nothing converts between currencies, so the field records the unit of account and no decision reads it | at what boundary does a budget ceiling stop being a number and become a currency — the routing table's own unit price, the ledger, or the caller's invoice |

### Gaps this example exposed

| # | Claim that is not supported here | Research query |
|---|---|---|
| 1 | A refusal cannot carry the policy version. The concern's future state asks for "a typed, machine-readable failure naming the rule and the policy version", and the closed problem registry declares only `rule_id` on `policy-denied`: the version, the input digest, the decision point and the spend delta are all refused as members and survive only in the run report. `test.sh` section 8 measures exactly which four are dropped | what governs adding an extension member to a closed problem-type registry, and how does a caller discover which members a type carries |
| 2 | Two closed registries disagree. The isolation capability raises `isolation-operation-unsupported` (501) and the shared registry the platform renders through has no row for it, so the operator's 501 comes back marked `registry: absent` rather than being re-typed. Measured, not smoothed over | how are capability-local problem types reconciled with one platform-wide closed registry — a namespace per capability, a registration step, or one registry every capability must land a row in first |
| 3 | Reconnect attached to a unit the boundary had already destroyed. `open_session` succeeded and `inspect_containment` answered, because no operation on the isolation interface reports whether a unit is still drivable. The run report records it rather than hiding it | what does an agent runtime protocol say about opening a session on a unit whose process has ended — a typed refusal, a new session on a new unit, or undefined |
| 4 | The bundles are versioned and immutable and not signed. The digest of the canonical bytes is the version, and nothing produces or checks a signature, so "an immutable bundle" here means a file this example did not edit | what does a signed policy bundle look like end to end — who signs, what the verifier is, and where the verification sits relative to activation |
| 5 | Everything is steered one at a time. Every verb addresses a handle or an ask the caller already holds, and no capability publishes an operation that lists the units running or the asks waiting — so "fifty of them at once" is not a question this interface can be asked. It is the subject of `REF-docs/architecture/proposed/steer.json`, whose rows are all proposed and each carry the query that would close them | what listing or inventory operation do sandbox control planes publish for running units, and how is a cross-run approval inbox expressed as a capability operation |
| 6 | The decision journal does not outlive the process. Every decision is pinned to a bundle digest, `explain` re-evaluates that bundle rather than reading a narrative, and the journal it reads is a list on the engine object — so "replayable months later" is measured here as replayable within one run | what retention, indexing and access rules do production decision-log pipelines apply, and what is the smallest record that still supports replaying a decision against the bundle that produced it |
| 7 | An allow's lifetime is this runner's convention. The effect is decided before the pause and again after the resume because `fire_effect()` does it, and nothing in the decision the engine returns states the action it admits or how long it is good for — which is why `--carry-decision` is a one-line breakage | does any decision API carry a stated scope and lifetime on the decision itself, or is spend-on-use always the caller's discipline |
| 8 | The rule set is a fixture with no test corpus of its own. Two engines agree on every decision this example takes, which is a corpus of nine actions from one unit, not a decision corpus a rule author would ship | what does a policy test corpus look like for an agent platform — coverage of rules, of decision points, or of actions — and what is asserted when two engines disagree |
| 9 | Nothing here is a real engine. Both adapters evaluate in process, so "swapping the decision language is configuration" is measured across two execution models and claimed against two products; and the decision's cost at fleet rate is not measured at all | run the same corpus against two live decision engines and compare the answers, the rule ids, and the two halves of the latency — input assembly and evaluation |
| 10 | The area has a visible check and no hidden one. The index expects a held-out check outside `examples/`; this author's brief permits touching only `examples/steer/` and `docs/architecture/proposed/steer.json`, so the area is, by the skill's own rule, incomplete rather than passing | where does an area's held-out check live, who writes it, and what does the index report for an area with a README and no hidden check |
