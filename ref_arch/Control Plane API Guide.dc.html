Platform · Developer guide

Control Plane API: multi-tenant data model, lifecycle and operations

How a system calls the control plane, how an organisation is onboarded with its own identity, secrets, storage and model routers, and how the service is started, run and kept healthy for many tenants and many users. Every boundary names the standard it adopts, so a tenant component that speaks the standard plugs in without a bespoke adapter.

Audience · platform engineers, tenant integrators, SRERouter seams (commands, read models, events) are the Router pages in the nav
{{ pageNum }}Quickstart

From an idea to fifteen agents in five minutes

Sign in, create a sandbox with a budget, say what you want, and run it. You see the price before anything spends and the first landing within minutes.

One CLI, cp, wraps the API. It never speaks a private dialect: every command is one HTTP call you can see with --dry-run. Pick your surface per step below; the CLI is the default, Node uses the generated SDK, and HTTP is the raw call for integrators.

Composable by default

A template (research, refactor, review, pipeline, triage) carries best-practice steps, acceptance criteria, model class and ceiling. You supply the intent.

Right model, low cost

The Planner assigns a class per step: free local for grunt work, batch for bulk, interactive for judgement, coding CLI for code. You can pin, but rarely need to.

Budget before spend

Every plan is priced before dispatch. Ceilings sit at task, workflow, sandbox and org. Exceeding one stops that unit, nothing else.

1
Sign in

Uses the identity provider your organisation bound at onboarding. A system uses an API key; the CLI exchanges it for a scoped token automatically.

npm i -g @cellplane/cli
# opens your IdP; stores a short-lived token
cp login
# for systems: RFC 8693 exchange, same token shape
cp login --api-key $CP_API_KEY
 
import { CellPlane } from "@cellplane/sdk";
// or interactive
const cp = await CellPlane.login({ apiKey: process.env.CP_API_KEY });
 
POST /v1/auth/exchange
subject_token=<api key>&audience=cellplane
# returns { access_token, expires_in: 900 }
You have: a scoped token in your keychain.
2
Create an environment

A sandbox is a project with its own budget, allowed tools and default class. It is where your tasks live and what the control plane shows you.

# writes cellplane.yaml in this folder
cp init
cp project create vendor-review --budget 40 --class i-
cp budget set --project vendor-review --per-task 0.60 --alert 80%
 
const prj = await cp.projects.create({ name: "vendor-review", budget: 40, defaultClass: "i-" });
await prj.budget.set({ perCell: 0.60, alertAt: 0.8 });
 
POST /v1/projects  { "name": "vendor-review", "budget_ceiling": 40, "default_class": "i-" }
PUT  /v1/projects/prj_a1/budget  { "per_task": 0.60, "alert_at": 0.8 }
3
Turn the idea into a plan

Say what you want. The template adds the steps and acceptance criteria; the Planner splits the work into units, assigns a class to each step and prices it. Nothing runs yet.

cp spec "Summarise each vendor's public security docs into our posture template, cite every claim" \
  --template research --inputs vendors.csv
# plan_8f1 · 15 units · steps: fetch (f-) → extract (b-) → draft (b-) → evaluator (i-)
# est $3.30 · ceiling $9.00 · fits budget ($40.00)
# edit: cp spec edit plan_8f1
 
const plan = await prj.plan({
  intent: "Summarise each vendor's public security docs into our posture template, cite every claim",
  template: "research", inputs: await csv("vendors.csv") });
// 15, { estimate: 3.30, ceiling: 9.00 }
console.log(plan.units, plan.cost);
 
POST /v1/task-specs  { "intent": "…", "template": "research", "inputs": [ … ] }
# returns { "id": "spec_8f1", "rev": 1, "plan": { "units": 15, "steps": [ … ] }, "cost": { "estimate": 3.30, "ceiling": 9.00 } }
4
Run it

Dispatch turns the plan into tasks: one agent per unit, each in its own microVM with its own ceiling. The run is idempotent; re-running the same plan returns the same tasks.

# → wf_9c · 15 tasks dispatched · first landing expected ≈ 40s
cp run plan_8f1
# start smaller, scale after the first landings
cp run plan_8f1 --tasks 5

# ~40s later
# t-1001 completed · evaluator PASS · $0.19 · acme.posture.md → s3://…/vendor-review/
 
// { workflow: "wf_9c", tasks: 15 }
const run = await plan.run();
 
POST /v1/workflows  { "task_spec": "spec_8f1", "rev": 1, "intake": "cli" }
POST /v1/workflows/wf_9c/dispatch  Idempotency-Key: plan_8f1  { "count": 15 }
You have: a sandbox with a hard budget and a config your team can commit.
You have: a priced, editable plan. Nothing has spent.
You have: fifteen agents running and the first result on disk.
5
Watch, and step in only when asked

Ladders handle the first attempts on their own. When a task is parked or exhausted, the CLI tells you and one command clears it. Or open the control plane.

# live: 11 running · 2 waiting · 1 stuck (ladder: restart 1/1) · 1 completed
cp watch wf_9c
# applies to the Task specification, replans, resumes
cp fix t-1009 --redefine "cite a URL that resolves"
# opens this workflow in the control plane
cp open wf_9c
 
for await (const ev of run.watch()) if (ev.needsYou) await ev.task.redefine({ acceptance_criteria: [ … ] });
 
GET  /v1/event-stream?workflow=wf_9c  (SSE)
POST /v1/tasks/t-1009/commands  { "verb": "redefine", "args": { "acceptance_criteria": [ … ] } }
You have: a fleet that mostly fixes itself, and one command for the rest.
6
Land it, and let it learn

When tasks land, results go to your storage binding and the ledger. Recurring problems become recommendations with a proposed Task specification edit; apply one and the template improves for next time.

# 15 files, provenance attached
cp results wf_9c --out ./posture/
# "tool-timeout ×4 in research → raise fetch ceiling to 120s"  apply? y
cp recommendations
# share the improved template with your org
cp template publish my-research
 
await run.results().download("./posture/");
const f = await prj.recommendations(); await f[0].apply();
 
GET  /v1/recommendations?window=7d
POST /v1/recommendations/rec_1/apply
# returns { "task_spec": "spec_8f1", "rev": 2 }
You have: results with provenance, and a template that is better than when you started.

{{ pageNum }}Shape of the service

One API, four tiers of scope, every call stamped with all four

Four scope ids (org, project, principal, task) travel on every request, event and row. Scope lives in the token, never in the URL.

The control plane is a single HTTP+SSE service in front of the core (Task specification, Planner, Graph, Evaluator, Ledger) and the capability adapters. Tenancy is not a deployment mode; it is a set of scope ids that travel on every request, every event and every stored row.

TierIdOwnsIsolation guarantee
Organisationorg_idIdentity provider binding, billing account, secrets namespace, object store bucket or prefix, model router endpoints, retention policyHard. Separate encryption keys, separate policy bundle, separate Ledger partition. No query crosses an org boundary.
Projectproject_idTask specifications, workflows, playbooks, saved groups, budgets, alert preferencesSoft. Same org keys; row-level scope on every table; policy may grant cross-project read to org admins.
Principalsub (OIDC)A user or a delegated agent actor. Roles are per project.Every command names the principal. Delegation chains (act claim) are recorded, never flattened.
Tasktask_idOne agent run in one microVM under one Task specification revisionRuntime isolation per the OCI Runtime Spec. Budget budget ceiling terminates the task, not the platform.
Scope is in the token, not the URL

org_id and project_id are claims on the OIDC access token (or on the exchanged token for agents). Paths never carry tenant ids, so a leaked URL leaks nothing and a mis-scoped client cannot address another tenant by guessing.

Every row, every event, every span

The four ids are mandatory columns in the Ledger, mandatory attributes on CloudEvents and OTLP spans, and mandatory inputs to every policy decision. A row without them is rejected at write time.

{{ pageNum }}Onboarding an organisation

Eight calls, each reversible, each verified before the next

Eight idempotent calls bind identity, keys, secrets handles, storage, routers and policy. Each has a machine-checked acceptance criteria.

Onboarding is a Task specification too: declared intent, a acceptance criteria per step, and a Evaluator check that must pass. A failed step leaves the org in provisioning with a typed problem, never half-configured.

#CallWhat it bindsAcceptance criteria (machine-checked)
1POST/v1/orgsName, region, retention. Returns org_id in provisioning.Row exists; Ledger partition created with genesis hash.
2PUT/v1/orgs/{id}/identityOIDC issuer URL, audience, role-claim mapping, optional SPIFFE trust domain.Discovery doc fetched; JWKS cached; a test token from the issuer validates.
3PUT/v1/orgs/{id}/keysKMS key reference for envelope encryption of the org's secrets and Ledger-at-rest.Encrypt/decrypt round-trip of a nonce succeeds with the tenant's key.
4PUT/v1/orgs/{id}/secrets/{urn}Registers a secret handle pointing at the tenant's vault path. Values never transit this API.Resolve returns a value of non-zero length; value is not logged (assert absent in trace).
5PUT/v1/orgs/{id}/storageS3 endpoint, bucket, prefix, scoped credential reference, SSE mode.PUT + HEAD + GET + DELETE of a probe object succeed; ListBucket outside the prefix is denied.
6PUT/v1/orgs/{id}/routersOne binding per model class: endpoint, key reference, per-task ceiling, model list.A 1-token completion succeeds per class; a request over ceiling is refused by the gateway, not merely recorded.
7PUT/v1/orgs/{id}/policyRego bundle URL or inline bundle; decision endpoint if bring-your-own.Bundle compiles; the platform's canonical deny test (spend over ceiling) returns deny.
8POST/v1/orgs/{id}/activateRuns the conformance suite across all bindings; flips to active.All step checks green in one run; evidence record written with the run's tree hash.

Two things the platform will not do for a tenant. It will not store a secret value (only a reference) and it will not proxy to a router that failed the over-ceiling refusal test. Both are measured recommendations from Part A (A4, A7-3): recording spend is not enforcing it, and configuration that validates but has no runtime effect is worse than none.

{{ pageNum }}Lifecycle API

From a Task specification to a completed task, and back to a better Task specification

Task specification → plan and price → workflow → dispatch → watch → commands → recommendations. Five calls cover the loop; no client library required.

This is the project-level surface a system integrates against. Every call below is fully specified, with parameters, schemas, errors and a Try-it panel, in the API reference.

Every error is typed, none is parsed from prose

Every non-2xx is an RFC 9457 problem with a stable type URI and a stated next step. Task-level problems use the same registry.

RFC 9457 application/problem+json on every non-2xx. The type URI is stable and resolvable at /v1/problem-types/{name}. Task-level problems (the Lenses) use the same registry.

{{ pageNum }}Start, run, maintain

Operating the control plane for many tenants

Stateless replicas, one writer per partition, ceilings at four levels, per-tenant rate limits and telemetry. One config file.
Start

One container image, one config file, all tenant state external. Boot order: Config store → Ledger head verification per partition → adapter conformance (fast subset) → HTTP/SSE listeners. A failed partition verification starts the service in read-only for that org and raises ledger-integrity; other orgs are unaffected.

Run

Stateless API replicas behind a load balancer; SSE sticks by project_id hash. One State writer per partition holds a lease (TTL 10s, renewed at 3s); replicas forward writes to the lease holder. Ladder execution is a scheduled job per project, bounded by the Playbook limits, actor ladder:.

Maintain

Config migrations are additive only; Ledger is never migrated, only re-projected. Adapter upgrades run conformance in a canary org before rollout. Retention job per partition nightly: export to tenant storage, verify, then trim. Every job writes evidence.

{{ pageNum }}Versioning and compatibility

Additive by default, breaking by new major

Additive by default. Paths carry /v1, events version by suffix only on breaking change, the Ledger is never rewritten.
SurfaceRule
HTTP paths/v1 in the path. A new major runs alongside the old for one retention window. Deprecations announced in Sunset and Deprecation headers (RFC 8594).
BodiesUnknown fields ignored on input, never emitted on output without a version bump. All schemas published as JSON Schema 2020-12 at /v1/schemas/{name}.
Eventstype is versioned by suffix only when the data shape breaks: cellplane.task.status.changed.v2. Consumers subscribe by prefix.
Problem typesRegistry at /v1/problem-types. New types are additive; a type is never repurposed. Retired types remain resolvable.
AdaptersConformance suite version travels with the adapter registration. An adapter passing suite N is not assumed to pass N+1.
LedgerRecord envelope carries schema_rev. Projections are rebuilt from the chain; the chain itself is never rewritten.

{{ pageNum }}Router · Principles

Six rules the router inherits from the architecture

The UI never talks to a product

It talks to the Dispatch, State, Telemetry and Policy interfaces. LiteLLM, Temporal, Langfuse and Firecracker appear only as today's adapters.

Every command is a typed intent

Nudge, Redefine, Escalate, Extend, Restart, Reassign, Cancel, Approve, Reject, Return. No free-form prompts cross the boundary from the phone.

Cross-cutting concerns are applied, not requested

Identity, budget, policy, provenance and idempotency are stamped on every command by the router. The client cannot omit them.

The grader stays invisible

The user sees the Evaluator criterion; the agent never does. Redefine edits the Task specification, then the Planner re-runs. The UI never pushes a criterion into a session.

Errors are RFC 9457, never prose

Each stuck reason in the UI maps to a problem type URI. The lens grid is a group-by on type.

Correlation rides on attributes

Per recommendation A7-1, the UI joins on task.id and spec.id resource attributes, never on trace parentage.

{{ pageNum }}Router · The loop

Recommendations and proposals are Ledger queries with a write-back

Observe

Every problem.raised is appended to the Ledger with type, Task specification, spend at failure.

Detect

A recommendation is any (Task specification, type) pair with recurrence ≥ 2 in the window.

Propose

Each type has a proposal template targeting Task specification, dispatch config, or schedule.

Apply

Operator-only. Writes a Task specification revision; provenance record names actor and prior hash.

Measure

Recurrence since the revision vs before. Revert is a further revision, never a delete.

EndpointBehaviour
GET/v1/recommendations?window=7dGrouped Ledger read. Includes count, costLost, nudges, proposal, applied, recurrence.before / since.
POST/v1/recommendations/{id}/applyCommand. Routes to State (Task specification revision) or dispatch config. Policy-checked. Returns the new revision id.
POST/v1/recommendations/{id}/dismissOperator judgement recorded in the Ledger; the recommendation is suppressed for the window.
POST/v1/task-specs/{id}/revisions/{rev}/revertNew revision equal to the prior content. The chain stays intact.

Guardrail. The loop proposes edits to what the agent is asked (intent, steps) and how it is run (ceiling, class, backoff). It never edits the Evaluator criterion by itself; a acceptance criteria change is a user command with a provenance record, so the grader stays outside the graded system (B1 rule 6).
